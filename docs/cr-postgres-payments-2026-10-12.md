# PostgreSQL 与支付消息记账合并审查

审查范围为 Android UI PR #18 和其后的 PostgreSQL／支付消息 PR #19。初始头提交分别为 `84aaae2`、`8b0f444`，按依赖顺序合入 main。源代码审查覆盖原生配置、金额与图表展示、支付通知队列／确认恢复、服务端事务与权限、旧库导入及容器切换流程。

## 已修复问题

| 级别 | 问题与触发条件                                                                                                    | 修复                                                                                                 |
| ---- | ----------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| P1   | 两个开放 API 记账请求使用同一幂等键同时提交，第二个请求获得已保存结果，却按自己新生成的 ID 查找，返回回执缺少账单 | 从持久操作的历史快照与结果识别实际新增记录，重试返回同一完整回执                                     |
| P1   | 同一附件幂等键并发提交，事务外的回执检查同时未命中，造成重复审计；不同负载也可能都成功并产生额外附件              | 锁账本后重新检查令牌和回执，重复请求复用结果，不同摘要返回 409，附件与审计仅写一次                   |
| P1   | 同步账本完成联网转换后，先前通过旧状态检查的 PUT 可携带新版本覆盖已转换内容                                       | 同步写入在同一事务锁账本、检查会话及当前 authority／schema，更新仍要求 snapshot authority 与版本一致 |
| P1   | 同一暂存附件被两个联网转换同时认领，或在转换期间被旧删除请求移除，留下不存在或归属错误的凭证引用                  | 转换按稳定 ID 顺序锁附件；事务内读取和清理同样锁行，等待后重新检查归属                               |
| P2   | 创建令牌的初始权限检查后，成员在事务开始前被降为只读，仍可创建带写入 scope 的令牌                                 | 在账本锁内重新检查当前角色；只读成员创建写入 scope 返回 403。使用令牌时的原有权限校验继续保留        |

新增七项真实 PG 并发测试。用原始 `8b0f444` 实现独立重放，七项均失败；应用修复后七项全部通过。其中同一记账／附件请求的重试、附件冲突、转换与删除、旧同步写入和角色降级均有实际数据库行为断言。测试只使用合成账本和隔离 schema。
